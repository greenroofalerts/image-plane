## Step 3: the 86 <=150m-unmatched mystery — SOLVED

Root cause confirmed by direct join, not guessed: **85 of the 86** were never in
`kept_deduped.jsonl` — the survivors set `allocate_global_v3.py`'s original run actually reads
GPS from — even though they carry a `keep` verdict in `classified.jsonl` and have GPS in
`geolocations.jsonl`. The matcher's input set (11,927 rows) is narrower than the true keep set
(12,338) by exactly this kind of gap; these 85 photos were geographically matchable all along
but were structurally invisible to every past run of the matcher. The F2 rerun uses
`classified.jsonl` keep-verdict paths directly (matching `counts.py`'s own derivation) instead
of `kept_deduped.jsonl`, so this class of photo is now correctly in scope. The remaining **1 of
86** carries `excluded: duplicate_lee_20260708` — correctly excluded by a prior Lee ruling, not
a bug.

## Step 4: rerun gps_nn against the grown map

**Hard-rule guard added and enforced (found during this pass, not anticipated by the spec
text):** a path already carrying ANY row in the pre-existing `allocation_v2.jsonl` — even a
flagged one (`excluded`, or `job_ref: null` from a prior misfile correction) — reflects a
considered decision by an earlier pass and must never be re-derived. First dry-run attempt
produced 193 candidate rows and, on inspection, 9 of those were exact duplicates of paths a
prior pass had deliberately excluded (`lee_ignore_guess_r1_20260708`) or demoted to
`job_ref: null` (`misfile: guess-r1-row7_year_sanity`, 8 rows, job 1712-24 "corrected away"
previously). That first attempt was reverted in full (allocation_v2.jsonl restored to its exact
pre-F2 7,099-row state, verified by line count and zero `_f2`-tagged rows) before any flags
rebuild or counts run touched it. The script was then fixed to skip any path with a prior row of
any kind, and rerun cleanly.

**Clean, applied result:**
- Target set: 4,966 unallocated-GPS keeps. Of these, 112 already carried a prior
  (flagged/considered) row and were skipped untouched. Genuine F2 candidate set: 4,854.
- **184 new allocations appended** (method `gps_nn_f2` 177 / `date_only_active_f2` 7 — the
  latter via the same same-postcode-cluster-split resolver `allocate_global_v3.py` already
  uses, reused verbatim, for the 17 <=35m ambiguity clusters present in the grown 209-job map).
- Confidence band tally: **high 116 / medium 37 / low 31** (bands unchanged from the
  established method: <=80m/<=150m/<=300m).
- **20 photos excluded as genuinely ambiguous** (two distinct candidate jobs both qualifying
  in-band, margin <40m, not resolved by the postcode-cluster splitter) — not forced, tallied
  for the Lee sheet (`grind/f2_ambiguous_excluded.json`).
- **Conflicts with existing allocations caused BY this pass's map growth: 0**
  (`grind/f2_conflicts.jsonl`, empty).

**Anomaly found and reported, not fixed (out of scope for F2):** re-checking ALL 6,563
pre-existing allocated keeps against the grown map's nearest-neighbour found **488** where a
DIFFERENT job than the one currently assigned is now nearest — but in every one of the 488
cases the "closer" candidate is a job that was **already in the original 198-job map**, not one
of this pass's 11 new entries. Root cause: `allocate_global_v3.py` computes a centroid-refined
coordinate for jobs with >=3 round-1 GPS matches and uses THAT refined coordinate for its actual
round-2 matching decisions, but persists the UN-refined coordinate to `job_coords.json`. The
persisted map has therefore never matched the coordinates the original allocator actually used
internally for some jobs. This predates F2 entirely, is not something F2 created, and existing
allocations were left untouched per the hard rule either way — flagged here for a future pass
(`grind/f2_preexisting_coord_drift_anomaly.json`, 488 rows) rather than silently absorbed into
the F2 conflict count.
